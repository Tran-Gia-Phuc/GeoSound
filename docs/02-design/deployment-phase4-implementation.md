### 3.0 Frozen interfaces (read by every task)

**Node, `shared/metrics/index.js`** (new export `./metrics` in `shared/package.json`, dependency `prom-client` ^15):

```js
// One registry per process. `service` becomes a constant label on every metric.
export function createMetrics({ service, collectDefault = true }) // returns:
// {
//   registry,                                      // prom-client Registry
//   counter({ name, help, labelNames }),           // returns { inc(labels, n = 1) }
//   histogram({ name, help, labelNames, buckets }),// returns { observe(labels, seconds), startTimer(labels) }
//   gauge({ name, help, labelNames }),             // returns { set(labels, v), inc(labels), dec(labels) }
//   httpMiddleware(),                              // Express middleware: http_requests_total, http_request_duration_seconds
//   registerMetricsRoute(app),                     // GET /metrics, text format, no auth
// }
```

- `httpMiddleware` labels: `method`, `route` (`req.baseUrl + req.route.path`, else `unmatched`), `status`. It skips `/metrics`, `/healthz`, `/readyz`, `/health`. Duration buckets: `0.05, 0.1, 0.25, 0.5, 1, 2.5, 5`.
- `shared/rabbitmq` gets `useMetrics(metrics)`. Once called:
  - `publish` increments `events_published_total{event}`;
  - `consume` increments `events_consumed_total{event, result}`, with `result` ∈ `ack`, `nack`, `skip`.
  - Without the call nothing changes (old callers keep working).
- Use cases outside `src/index.js` never import `shared/metrics`. They get a small port (for example a `moderationMetrics` object) from `container.js`, built from the `counter` / `histogram` / `gauge` factories that `index.js` passes in. **Services do not add prom-client to their own `package.json`** (it comes with shared); only the gateway does.

**Python, `services/ai/app/metrics.py`** (new; `prometheus_client` and `prometheus-fastapi-instrumentator`, both pinned in `requirements.txt`):

- Module-level metrics with the names and labels of plan 10.2: `llm_requests_total`, `llm_request_duration_seconds`, `llm_fallback_total`, `chatbot_requests_total`, `chatbot_first_token_seconds`, `chatbot_indexer_events_total`.
- `setup_metrics(app)`: instrumentator on the app, `GET /metrics` not in the OpenAPI schema and **without** `x-internal-token`, excluding `/metrics` and the health routes.

**Scrape contract:** every backend app serves `GET /metrics` on its `http` port. The client (nginx) has none.

Branch `feature/deploy-monitoring-stack`.

**Steps:**

1. **Pin chart versions:** `helm search repo prometheus-community/kube-prometheus-stack --versions`, the same for `grafana/loki` and `grafana/alloy`. Write the chosen versions in the Applications and the runbook. Do not guess version numbers.
2. **Applications** in namespace `argocd`, project `default`, destination namespace `monitoring`:
   - Multi-source: the Helm chart from its repo, plus `ref: values` on `https://github.com/Tran-Gia-Phuc/GeoSound.git`, `targetRevision: staging`.
   - `releaseName: kube-prometheus-stack` (the ServiceMonitor label `release: kube-prometheus-stack` depends on it).
   - `syncOptions: [ServerSideApply=true]` (the Prometheus Operator CRDs are too big for client-side apply).
   - Automated sync with prune and self-heal.
   - For the first check use the feature branch as `targetRevision` and say so in the PR; the committed file says `staging`.
3. **kube-prometheus-stack values:**
   - Disable `kubeEtcd`, `kubeControllerManager`, `kubeScheduler`, `kubeProxy` (k3s embeds them; their targets would always be down).
   - Prometheus: `retention: 2d`, `retentionSize: 2GB`, 3 Gi `local-path` PVC, requests 300Mi / limit 900Mi, scrape interval 30s.
   - Prometheus selects ServiceMonitors and PrometheusRules with label `release: kube-prometheus-stack` in all namespaces (`serviceMonitorNamespaceSelector: {}`, `ruleNamespaceSelector: {}`).
   - Grafana:
     - `admin.existingSecret: grafana-admin`, persistence off, `grafana.ini` with anonymous auth off.
     - Dashboard sidecar on (label `grafana_dashboard: "1"`, all namespaces).
     - Loki as an extra datasource (`http://loki:3100`).
   - Alertmanager: one replica, small limits, config left for 4.7 (keep the default null receiver for now).
   - node-exporter and kube-state-metrics on, with small limits.
4. **Loki values:**
   - `deploymentMode: SingleBinary`, one replica, filesystem storage, 3 Gi PVC.
   - Compactor retention on with `retention_period: 48h`.
   - **Disable `chunksCache` and `resultsCache`**: the chart's memcached defaults ask for several GiB.
   - Disable `gateway`, `lokiCanary`, `test`, and the read / write / backend replicas.
5. **Alloy values:** DaemonSet. Pipeline:
   - `discovery.kubernetes` (pods) → `loki.source.kubernetes` (API tailing, no hostPath) → `loki.process` → `loki.write`.
   - Labels: `namespace`, `app` (`app.kubernetes.io/name`), `service`, `level` (parsed from the JSON line).
   - `reqId` goes to structured metadata, **not** to a label.
   - A `stage.replace` that rewrites `https://(discord|discordapp)\.com/api/webhooks/\S+` to `<redacted-webhook>` on **every** line.
   - Collect namespaces `geosound-staging`, `monitoring`, `argocd`.
6. **Stop the leak at the source too:** checked on 2026-11-16, the log level is already `info`: the `[DEBUG] POST` line comes from the default logger of go-retryablehttp, which ignores the log level. So `values-local.yaml` is not changed; Alloy drops that line and redacts webhook URLs (step 5). Check that no new `POST https://discord` line appears in `kubectl -n argocd logs deploy/argocd-notifications-controller`; only `grep -c` the lines, never print them.
7. **Grafana admin secret (agent, never printed):**
   - Generate a random password into `~/.kube/geosound-grafana-admin.txt`.
   - Run `kubectl -n monitoring create secret generic grafana-admin --from-literal=admin-user=admin --from-file=admin-password=<that file>`.
   - Strip the trailing newline before creating the secret.
8. **Install (U1):**
   - Apply `deploy/argocd/apps/monitoring.yaml` and wait until all four Applications are Synced and Healthy.
   - Port-forward Grafana to `127.0.0.1:4468`, Prometheus to `:4469`, Alertmanager to `:4470` as background tasks.
9. **Measure:** `kubectl top node` and `kubectl -n monitoring top pod` before and after. Write the numbers in the runbook.

- [ ] The four Applications are Synced and Healthy; every pod in `monitoring` is Running and none restarts for 15 minutes.
- [ ] Sum of memory requests in `monitoring` ≤ 1.5 GiB; node memory after install < 80 %.
- [ ] Grafana opens on `127.0.0.1:4468`: login works with the generated password and anonymous access is refused. The Prometheus and Loki datasources both test OK.

## 4. Parallel work and sub-agents

The main agent owns git, the issues, the cluster and the final answer. Sub-agents only edit files and run tests, each in its own worktree (`/e/CNPM/git/wt-<N>`, created by the main agent from the issue branch). They never run git write commands and **never touch the cluster**: every `kubectl` / `helm` step and every live check is done by the main agent, one at a time.

### Wave A: five sub-agents at the same time

All five start right after the issues exist. They touch disjoint files (checked in the **Files** lists above), and P4-8 freezes the shared API they depend on.

| Task | Sub-agent | Worktree | Writes only in | Depends on |
| --- | --- | --- | --- | --- |
| 4.1 stack (files only) | `general-purpose` | `wt-<4.1>` | `deploy/argocd/`, `deploy/monitoring/`, `scripts/deploy/check-chart.sh`, runbook | none |
| 4.2 Node metrics | `general-purpose` | `wt-<4.2>` | `shared/`, `gateway/`, `services/{auth,tour,media,notification}/src/index.js` | none (it builds the 3.0 API) |
| 4.3 AI metrics | `ai-python-dev` | `wt-<4.3>` | `services/ai/` (not translation) | none |
| 4.4 Moderation metrics | `moderation-node-dev` | `wt-<4.4>` | `services/moderation/` | the 3.0 API **contract only**: unit tests use a fake port; the `index.js` wiring is tested once 4.2 is merged |
| 4.5 ServiceMonitors | `general-purpose` | `wt-<4.5>` | `deploy/helm/geosound/`, `deploy/local/values.yaml` | none for the files (kubeconform uses the CRD catalog) |

4.5 fits in wave A because it only touches the chart. To keep at most four agents at once, start 4.5 as soon as one of the other four finishes.

While wave A runs, the main agent installs the stack of 4.1 on the laptop from its feature branch (step 8), because only that step needs the cluster.

**Merge order inside wave A:** 4.2 first (4.4's `index.js` imports `shared/metrics`), then 4.3, 4.4, 4.5 and 4.1 in any order. After that, one PR `develop` → `staging` (U3), and the main agent runs the live checks of 4.1 to 4.5.

### Wave B: two sub-agents at the same time

Wave B starts after wave A is deployed, because both tasks need real data in Prometheus and Loki.

| Task | Sub-agent | Worktree | Writes only in | Depends on |
| --- | --- | --- | --- | --- |
| 4.6 dashboards | `general-purpose` | `wt-<4.6>` | `deploy/monitoring/dashboards/` | wave A live |
| 4.7 alerts | `general-purpose` | `wt-<4.7>` | `deploy/monitoring/alerts/`, Alertmanager block of `values/kube-prometheus-stack.yaml`, alert sections of `deploy/README.md` | wave A live, U2 |

They do not conflict, because 4.1 already created separate `kustomization.yaml` files for `dashboards/` and `alerts/`. The dashboard JSON is exported from Grafana by the main agent (port-forward) and handed to the sub-agent to clean and commit-ready; the sub-agent cannot reach the cluster. After both merge: one PR `develop` → `staging` (U3) and the test alert of 4.7.

### After each task (sequential, main agent)

1. `test-runner` runs the suites of the task once.
2. `contract-reviewer` checks:
   - no secret or webhook URL in the diff, values or logs;
   - label cardinality and privacy (P4-6);
   - the CI rule for `../shared` imports;
   - git hygiene.
   Fix every FAIL; the re-review checks only the FAIL items.
3. The main agent commits with explicit paths, shows `git log --oneline` and waits for the user before any push.
